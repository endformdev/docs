Connect your coding agent to the [Endform MCP server](/docs/reference/mcp-server), then ask questions about the test history for the repository you are working in. The agent can compare trends, inspect individual executions, compare a failed attempt step by step with a passing run, and link you to a replay of what it found, without you copying data out of the dashboard.

The conversations below are representative examples. Your results will use your own tests and Endform history.

<Conversation title="What are our flakiest tests?" open>
  <UserMessage>
    What were our flakiest tests over the last seven days? Look into the worst one and tell me why it flakes.
  </UserMessage>

  <ToolCall name="analytics_query" summary="passing test runs with retries, grouped by test, last 7 days" />
  <ToolCall name="samples_query" summary="recent retried executions of the flakiest test" />
  <ToolCall name="test_attempt_inspect" summary="compare a failed attempt with its passing retry" />
  <ToolCall name="test_attempt_inspect" summary="check another failed attempt of the same test" />
  <ToolCall name="test_attempt_replay_link" summary="replay the failed click beside the passing retry" />

  <AssistantMessage>
    `checkout.spec.ts › saved card › completes payment` was the flakiest test this week. It passed in 18 runs, but 6 of those runs needed a retry.

    The failed attempts have the same pattern: the test clicks **Pay now** immediately after the saved card request finishes, but before the form enables the button. The successful retries wait long enough for that state transition. In both failed attempts, the first change from the passing retry is the click on a disabled button, and there is no corresponding `POST /payments` request. I've linked a replay that plays a failed attempt beside its passing retry, opened on that click.

    I would replace the fixed delay before the click with an assertion that the button is enabled:

    ```ts
    await expect(page.getByRole("button", { name: "Pay now" })).toBeEnabled();
    await page.getByRole("button", { name: "Pay now" }).click();
    ```
  </AssistantMessage>
</Conversation>

<Conversation title="Which tests are slowest?">
  <UserMessage>
    Which individual tests have the biggest effect on our test runtime? Check whether any have become slower recently.
  </UserMessage>

  <ToolCall name="analytics_query" summary="average test duration grouped by test, last 30 days" />
  <ToolCall name="samples_query" summary="recent executions of the slowest tests" />
  <ToolCall name="analytics_query" summary="daily duration trend for the leading slow test" />

  <AssistantMessage>
    `reports.spec.ts › exports a yearly CSV` is the largest individual bottleneck at an average of 48 seconds. It was averaging 29 seconds at the start of the month and has climbed steadily since August 8.

    The sample runs show that browser setup is stable; almost all of the increase is spent waiting for the export request. `organization.spec.ts › deletes a workspace` is second at 33 seconds, but its duration has not changed materially.

    I would investigate the yearly export endpoint first. Because Endform runs tests in parallel, reducing this longest test is more likely to shorten the overall feedback loop than optimizing several already-fast tests.
  </AssistantMessage>
</Conversation>

<Conversation title="Triage today's failures">
  <UserMessage>
    Summarize today's test failures. Group related failures together and tell me what to investigate first.
  </UserMessage>

  <ToolCall name="analytics_query" summary="failed test count grouped by test, last 24 hours" />
  <ToolCall name="samples_query" summary="latest failed executions and their ordered attempts" />
  <ToolCall name="test_attempt_inspect" summary="inspect a representative checkout failure" />

  <AssistantMessage>
    There are 14 failed test runs across three groups:

    1. **Checkout API unavailable: 9 failures.** Three checkout tests fail after the same `POST /payments` 503 response. This is the highest-priority issue because it affects every browser project and retries do not recover.
    2. **Profile menu timing: 4 failures.** These pass on retry and share a locator timeout. Treat this as one flaky-test issue.
    3. **Visual assertion: 1 failure.** The settings-page screenshot differs only in WebKit and did not retry.

    Start with the payments service or its test environment. The representative attempt shows the UI behaving normally up to the failed API response, so changing the Playwright assertions would only hide the underlying outage.
  </AssistantMessage>
</Conversation>

You can make these questions more specific by naming a branch, commit, Playwright project, test file, title, or time window. The complete historical data tool reference is in [Endform MCP server](/docs/reference/mcp-server#analyze-historical-test-data).
